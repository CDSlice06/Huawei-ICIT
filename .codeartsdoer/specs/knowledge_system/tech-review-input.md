# 技术评审输入（2026-09-07，来自用户外部技术评审）

> 用途：①需求阶段吸收其中的优先级调整与行为约束修改；②设计阶段（spec-design-agent）必须完整采纳第二、三部分的技术选型与实现建议。

## 一、技术风险与对应的需求修改

1. **范围膨胀（最大风险）**：v1.4的P1体量超过P0，报名截止仅剩不足3个月、团队3人。评审导向创新性60%+应用价值40%，看深度不看数量。
   - P0死守"导入→卡片→导图→复习"闭环
   - **P1只挑错题本做深**（场景痛点最真实、与复习叙事最连贯）
   - **论坛、拼图自测降为P2**（决赛冲分再上）
2. **拼图自测+自由拖拽编排是最高技术风险**（自由画布拖拽、实时环检测、自动布局、打散算法、判定算法）。
   - 拼图自测降级为**"固定布局、逐层拼装"的简化版**且降P2，演示效果几乎不损失
   - 自由拖拽编排必须基于现成图编辑库实现（见选型）
3. **OCR路径定为MaaS多模态直接识别**（不选华为云OCR服务）：错题场景有手写体/数学公式/图形，传统OCR效果差且双服务串联重试复杂；多模态一次调用图片→结构化JSON。须**前端上传前压缩图片**（避免10MB原图直接喂模型）。
4. **异步任务机制**（5.3.1规则5"无需刷新"背后）：大模型调用30~120秒须异步执行——任务表+后台执行+前端SSE或2秒轮询；**禁止**Celery/RabbitMQ/WebSocket全家桶（单机ECS、50并发用不上）。
5. **逾期顺延的定时调度**：每日一次调度即可（APScheduler或cron），不引调度中间件。
6. **搜索实现**：1万条/2秒规模用MySQL 8 FULLTEXT+ngram分词+字段加权（标题>标签>要点>正文），**不引入Elasticsearch**。P2语义搜索：MaaS embedding+MySQL JSON存向量+内存暴力余弦比对（1万条毫秒级），无需向量数据库；决赛可换GaussDB向量能力。
7. **发布快照实现**：整体序列化为一份JSON（卡片集合+导图结构+**节点画布位置**）存RDS JSON字段；快照必须含节点位置否则浏览布局乱。

## 二、技术选型（设计阶段采纳）

| 项 | 选型 | 理由 |
|----|------|------|
| 后端 | **Python + FastAPI + SQLAlchemy** | 代码量少、AI生成质量高（配合码道）、异步/SSE标准能力 |
| 文档解析 | PyMuPDF（PDF）+ python-docx（Word） | 配合后端栈 |
| 前端 | **Vue 3 + Element Plus** | 码道生成效率高 |
| 思维导图 | **AntV G6 或 X6**（最关键选型） | 树布局/拖拽改父子/环检测/自定义节点位置现成，5.5三大交互工作量砍70% |
| 密码 | bcrypt/argon2 | 禁止自写MD5加盐 |
| 会话 | Redis存token | 简单直接 |
| 文件上传 | OBS前端直传（临时凭证） | 不经后端中转 |
| 部署 | **Docker Compose一键起前端+后端+Nginx** | 满足README一键运行开源要求+全球总决赛落地进展分 |

## 三、一句话总结

spec无逻辑硬伤，真正风险是功能清单大于三个月可交付量、拼图自测选型不当会吞掉整个迭代。技术栈围绕"码道生成代码效率+华为云资源清单最小化+演示效果"三点选定，综合最稳。
